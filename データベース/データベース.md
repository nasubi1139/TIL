# データベース
  正しい情報が表示されて当たり前　大前提の大事なとこ

データベースとは
  データを保存・管理する場所

  どう保管しているか
  ※リレーショナルデータベースの場合
    複数のテーブル(二次元表)がいくつもあり、テーブルごとにデータが入ってる

  イメージ
    データベース　･･･　図書館の書庫
    テーブル　　　･･･　書庫の棚
    データ　　　　･･･　本

  テーブルの構造
    名前(テーブル名)
    列(カラム)
    行(レコード)
    主キー(プライマリーキー)　･･･　データのレコードを一意に特定する
                                =>必須。データの被りがあってはいけない。

  注
    主キーが必ずあること
    一行で特定できること

  かぶってはいけない理由 => パフォーマンスが死ぬほど落ちる

  データベースの設計
    要件定義
    設計 <= ここ
    実装
    リリース

  ■何をデータとして保存するか
  ■どのような形式で保存するか

  ■何をデータとして保存するか
    ・システムで使用するもの(商品情報など)
    ・ユーザーが登録するもの(氏名や買い物かご等)
  ★★ポイント★★
      ・データを抽出する
      ・エンティティ(実体)を定義する
        抽出　=>　エンティティ
        (Notion参照)

  ■どのような形式で保存するか
    どんな表で保存するか考える
    一旦テーブルにいれてしまう
  ★★ポイント★★
      ・値を指定すれば１行のレコードを特定できる
      ・テーブル内に必ず１つだけ存在
      ・テーブルは重複データを持てない
      (Notion参照)


  ■第一正規形
    ・正規形　･･･　一貫性と効率性を持った形でデータを保存するためのデータ形式
    ・正規化　･･･　一貫性と効率性を持つようにデータベースを設計する
    ・第一正規形･･･1つのセルの中には1つの値しか含まない。効率よく検索できる。
  ★★ポイント：関数従属性★★
      ・y=f(x)：入力xに対して出力yが決まる
      ・yはxに従属する：{ x } => { y ](  xが決まればyの情報も自動で決まる )
      ・1つのセルに1つの値の方針も関数従属性(生徒IDが決まれば学部名まで埋まる)
      ・テーブル設計ではすべての列が関数従属性を満たすように整理していく

  【課題】
    オペレーションミスがあるとき
      登録データの変更時、1行変更忘れなど
      =>テーブルを分割する

      (Notion参照)
      【名前変更時】{生徒ID,科目ID}が主キー、{生徒ID}→{名前}の関数従属性がある
      →生徒テーブルを生徒・履修科目テーブルに分割

  ■第二正規形
    ・第一正規形から部分関数従属を排除
    ・部分関数従属　･･･　主キーの一部に対して従属する列がある
    ・テーブル分割でデータに矛盾がなくなる

  【課題】
    どれとも紐づかないと登録できないデータが存在
    {生徒ID}→{学部ID}→{学部名}の(多段階)関数従属性があり、必ず{生徒ID}が必要な状況になってしまっている
    =>テーブルを分割する


  ■第三正規形
    ・第二正規形から推移的関数従属を排除
    ・推移的関数従属　･･･　テーブル内に段階的な従属関係があり
    ・テーブル分割すると、ほかのデータと紐づかないデータも登録できる

  ★★ポイント★★
      ・第三正規形まで正規化すれば基本OK
      ・第六正規形まで存在するが、第三正規形までで十分なケースが多い
      ・データに矛盾が生じないことが何より重要

  【課題】
  テーブル同士の関係がわかりづらい
  => 図で整理

================================

  ■ER図
    ・テーブルとテーブルを線でつなぎ、中身の種類と関係性を見やすくしたもの
    ・テーブル間における関係として「1対1」「1対多」「多対多」がある
    ・書き方

  【1対1】
    ・あまり登場しない
    ・1つのテーブルにまとめればOK

    お互いからみて一つのテーブルとしかつながっていない
    一つのテーブルにまとめればよいのであまり登場しない

  【1対多】
    ・一番登場する
    ・正規化によって生まれる関連

    片方から見たら多数のデータと紐づくが、
    もう片方から見たとき一つのデータとしか紐づかない

  【多対多】
    ・多対多は登場するが、テーブル設計上はNG
    ・両方を紐づけることができない
    ・無理やり紐づけると正規化ができていない状態に

    対策
    中間テーブルを作成する　=> 「1対多」の関係となる
    正規化していけば自然となる形

  ■まとめ
    ・テーブルが増えていくと関係がわかりづらくなる
    ・ER図を使うことで関係を整理
    ・テーブル間の関係は基本的に「1対多」
    
================================

  テーブルの定義
    ・どう定義するか
    ・データ型・主キーの設定等なにをどうすればいいか

  ■テーブル定義時に考えること
    ・テーブル名
    ・カラム名
    ・データ型
        INT：整数を入れる列
        VARCHAR：文字列を入れる列
        DATE：日付を入れる列
    ・PK(プライマリーキー)　〇or空欄
    ・NOT NULL　NULLはダメって制約を設定するか否か
        基本的にダメ、処理が極端にめんどくなるパフォーマンスが落ちる
    ・デフォルト

  ★★ポイント★★
    ・「テーブル定義時に考えること」欄の項目を考えれば基本OK
    ・下記も考えれば完璧(後で調べよ)
        外部キー制約、ユニーク制約、チェック制約、オートインクリメント


  テーブル定義後にやること
    インデックス(索引)の設定
    パフォーマンス向上が目的
    最終チェック：使用を満たしているか

【まとめ：設計のポイント】
  ・要件を満たすテーブル/カラムを作成する
  ・必要データはアプリケーションが決める
  ・要件定義をしっかりと行い、理解する
  ・データに矛盾が生じないように正規化する

【まとめ：正規化のポイント】
  ・「第一正規形」1つのセルに値が1つだけか
  ・「第二正規形」主キーの一部だけしか利用していないのに一意に定まる列が存在していないか
  ・「第三正規形」主キー以外の列同士(多段階)で従属する列は存在していないか
